# Shared operation lifecycle: Mom and Loom

Source base: `1cee70d53605ba3bfba6a479e15eda308066ad21`. This change replaces shared lifecycle mechanisms in both production paths. It does not claim one application scheduler, one storage format, or live desktop acceptance.

## Replacement and production consumers

`crates/operation-lifecycle` is dependency-free safe Rust (`forbid(unsafe_code)`). It exports three small mechanisms:

- `InstanceId`: allocation identity with retained lifetime, not a serializable or forgeable public request name. Mom explicit operation handles carry the exact operation incarnation; Loom attempt identities carry the supervisor owner.
- `RunControl`: cancellation versus terminal arbitration. Every run/branch has its own control. `claim_terminal` returns `Some` to one claimant and `None` thereafter, preserving whether cancellation won first. Product code still decides result class and performs persistence/publication.
- `WorkerLedger`: all outstanding workers plus bounded recent joined diagnostics. Callers must own and consume the real join handle before noting a join. History is evicted in join order, not worker-ID order.

Production integration replaces Mom's duplicated `ChatCancelControl`/`MentionCancelControl`, both supervisors' per-attempt cancellation flags, and both supervisors' independent joined-worker bookkeeping. Existing product public DTOs and native worker ownership stay in place. Nothing is added solely for a proposed future consumer.

Mom's `SupervisedTask` retains a small completed-join observation so a slow consumer does not fail because its worker aged out of the recent diagnostic set. The observation is written only after the owner joins. Outstanding entries remain until then, including while a different caller is inside `join`.

## Concrete regressions

1. **Mom join versus shutdown:** block a real worker, move its handle into a concurrent reaper, invoke shutdown, and verify shutdown cannot return until that worker exits and joins. This exercises actual Rust threads and join ownership, not a mocked generation result.
2. **Mom foreign/stale explicit operation handles:** two owners create the same public ID; an old or foreign handle must neither cancel nor finish the other operation. A handle retained across public-ID reuse cannot start an attempt in the replacement operation.
3. **Loom foreign supervisor lease:** two supervisors allocate sequence 1 for the same request ID; the foreign lease must fail cancellation, queue, and child-attempt release. Validation happens before removing an attempt.
4. **Terminal races:** concurrent cancellation and terminal claiming have one linearized winner; replayed claims and late cancellation cannot reopen the operation. A completed Loom terminal snapshot does not acquire a new cancellation flag.
5. **Bounded retention:** thousands of joins retain bounded recent diagnostics while the oldest unjoined worker remains outstanding. Existing released-lease snapshots continue to work.

## Remaining boundaries

The complete supervisors are not interchangeable. Mom's wrapper owns threaded command execution and async result delivery; Loom's wrapper tracks nested attempts and coordinates separately owned forwarders and backend owners. Merging those public wrappers prematurely would require compatibility machinery and blur who actually owns a worker. The shared mechanisms above remove genuine duplication while keeping those responsibilities visible.

The next run-level consolidation should move the application admission/drain root into one application runtime, with an operation owner retaining the product-specific context, durable result sink, and actual workers. It must preserve chat branch cancellation, automatic-completion supersession, session-close persistence repair, tool approval recovery, and speech's non-preemptive Apple synthesis boundary. No timing, live model, window-close/reopen, or signed-bundle acceptance is established by these unit tests.

This slice is a correctness-first convergence step and may grow net source lines because it adds missing owner isolation, join synchronization, and regression coverage. It does not claim a code-size reduction for this class; later removal of one application composition root is the larger deletion opportunity.
